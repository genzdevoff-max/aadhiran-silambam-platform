## 1. Root Cause of Previous Deployment Failures

Two distinct build and deployment failures occurred previously:

### Failure 1: `cd backend: No such file or directory`
- **Root Cause:** In earlier deployment attempts, the Vercel Project **Root Directory** was set to `backend` in the Vercel dashboard or project configuration.
- **Evidence:** When Vercel sets the Root Directory to `backend`, the build process runs with working directory already set to `E:\...\backend`. When a build command like `cd backend && npm install && npm run build` (or `vercel.json` pointing to `backend/`) was executed, attempting to run `cd backend` failed because there was no nested `backend/` directory inside `backend/`.

### Failure 2: `[BUILD_FAILED] No entrypoint found in output directory: "N/A"`
- **Root Cause:** When deploying from the repository root (or without an explicit Serverless Function entrypoint):
  1. The repository root previously lacked a `package.json` and had an empty `package-lock.json`.
  2. The root contained legacy HTML template assets (`index.html`, `css/`, `js/`), while the modern React application was in `frontend/` and the Express API in `backend/`.
  3. `backend/src/server.ts` was executing `startServer()` unconditionally at import time, attempting to connect to TiDB and listen on a local TCP port (`app.listen()`).
  4. Vercel's platform could not detect a valid serverless entrypoint convention (such as an `api/` directory or recognized Express handler) to compile and expose the backend.

## 2. Final Single-Project Architecture

The platform is now configured to deploy as a **single, unified full-stack project** from the repository root:

```
aadhiran-silambam-platform/ (Repository Root)
├── api/
│   └── index.js              <-- Vercel Serverless Function entrypoint (routes /api/* to Express)
├── backend/
│   ├── src/                  <-- Express backend source (TypeScript)
│   ├── dist/                 <-- Compiled backend CommonJS
│   ├── package.json          <-- Backend dependencies & scripts
│   └── tsconfig.json
├── frontend/
│   ├── src/                  <-- React 19 + Vite SPA source
│   ├── dist/                 <-- Compiled static frontend assets (Vercel CDN output)
│   ├── public/uploads/       <-- Bundled static media assets
│   ├── package.json          <-- Frontend dependencies & scripts
│   └── vite.config.ts
├── package.json              <-- Root orchestrator (scripts for backend + frontend)
├── vercel.json               <-- Unified Vercel configuration (build, rewrites, function bundling)
└── .gitignore                <-- Ignores node_modules, .env, and temp files
```

### Architectural Highlights:
1. **Single Domain & Same-Origin Access:** Both the React frontend and Express backend are hosted under the same Vercel project domain. The frontend calls `/api/...` directly using same-origin relative URLs (`baseURL: '/api'`). This eliminates CORS preflight latency and avoids broken API URLs on preview deployments.
2. **Serverless Backend Export:** `backend/src/server.ts` conditionally guards `app.listen()` (`if (require.main === module)`). When imported by the Vercel Serverless Function (`api/index.js`), it exports the Express `app` cleanly without starting background listeners.
3. **CDN-Optimized Frontend Delivery:** Static files generated by Vite into `frontend/dist` are served directly by Vercel's global CDN before any serverless function or rewrite invocation.

## 4. Final Root `vercel.json` and Explanation of Routing

### Content of `vercel.json`:
```json
{
  "$schema": "https://openapi.vercel.sh/vercel.json",
  "installCommand": "npm --prefix backend install && npm --prefix frontend install",
  "buildCommand": "npm run build",
  "outputDirectory": "frontend/dist",
  "functions": {
    "api/index.js": {
      "includeFiles": "backend/dist/**"
    }
  },
  "rewrites": [
    {
      "source": "/api/:path*",
      "destination": "/api/index.js"
    },
    {
      "source": "/uploads/:path*",
      "destination": "/api/index.js"
    },
    {
      "source": "/((?!api/|uploads/).*)",
      "destination": "/index.html"
    }
  ]
}
```

### Routing Rules Explained:
1. **Static Assets (First Priority):** Vercel's edge network serves matching static files in `frontend/dist` directly (e.g. `/assets/*`, `/silambam.ico`, `/favicon.svg`, bundled `/uploads/*`).
2. **Backend API (`/api/:path*`):** Any request starting with `/api` is routed to the serverless function `api/index.js`. Express receives the full URL (`/api/health`, `/api/public/settings`, etc.) and matches its routes without requiring prefix stripping or route rewrites.
3. **Dynamic Uploads (`/uploads/:path*`):** If an uploaded media file is requested that is not in the static `frontend/dist/uploads` bundle, the request falls back to the Express static media handler.
4. **SPA Client-Side Routing (`/((?!api/|uploads/).*)`):** Any route that does **not** match `/api/` or `/uploads/` is rewritten to `/index.html`. This ensures React Router handles direct page navigation (e.g. `/about`, `/admin`, `/syllabus`, `/news/slug`) seamlessly upon refresh.
5. **No 404 HTML Masking:** Because `/api/:path*` routes explicitly to the Express function, non-existent API endpoints return a JSON 404 response from Express rather than accidentally serving `index.html`.

## 5. Root Build Commands and Package Configuration

### Content of Root `package.json`:
```json
{
  "name": "aadhiran-silambam-platform",
  "version": "1.0.0",
  "private": true,
  "scripts": {
    "install:all": "npm --prefix backend install && npm --prefix frontend install",
    "build": "npm --prefix backend run build && npm --prefix frontend run build",
    "build:backend": "npm --prefix backend run build",
    "build:frontend": "npm --prefix frontend run build",
    "test:unit": "npm --prefix backend run test:unit",
    "dev:backend": "npm --prefix backend run dev",
    "dev:frontend": "npm --prefix frontend run dev"
  }
}
```

### Build Flow:
1. Vercel executes `installCommand`: installs `backend` dependencies using `backend/package.json` and `frontend` dependencies using `frontend/package.json`.
2. Vercel executes `buildCommand` (`npm run build`):
   - `npm --prefix backend run build`: runs `tsc`, compiling backend TypeScript to `backend/dist/`.
   - `npm --prefix frontend run build`: runs `tsc -b && vite build`, bundling the React SPA into `frontend/dist/`.
3. Vercel identifies `outputDirectory: "frontend/dist"` and publishes it to the CDN.
4. Vercel packages `api/index.js` and all included `backend/dist/**` files into the Serverless Function runtime.

## 6. Backend Serverless Entrypoint Details

The entrypoint file `api/index.js` connects Vercel's serverless function runtime to the compiled Express application:

```javascript
// api/index.js - Vercel Serverless Function Entrypoint for Express API
const path = require('path');

// Load compiled Express backend application
const serverModule = require('../backend/dist/server.js');
const app = serverModule.default || serverModule;

module.exports = app;
module.exports.default = app;
```

- **Clean Export:** Exports `app` both as CommonJS default and module exports for compatibility with `@vercel/node`.
- **Zero Persistent Listener:** The server does not call `app.listen()`. Vercel manages the incoming HTTP request/response stream.
- **Serverless-Safe Uploads:** Temporary Multer buffer writes use `os.tmpdir()` (`/tmp/uploads`) rather than the read-only root directory.
- **Database Connection:** TiDB connection pooling initializes on first function invocation and persists across warm invocations.

## 9. Remaining Risks & Mitigations

1. **Cold Starts and TiDB Connection Pool:**
   - In serverless execution, mysql2 connection pools persist across warm lambdas but close on cold starts.
   - *Mitigation:* `connectionLimit` is set to 20 with `idleTimeout: 30000`, which is safe for TiDB serverless workloads.
2. **Backblaze B2 Media Downloads:**
   - As documented in Phase 2E, for private B2 storage, media assets should use presigned URLs (`getUrlForKey(key, isPublic = false)`) so that client browsers can download files with temporary 1-hour authentication signatures.
3. **In-Memory Rate Limiting:**
   - `express-rate-limit` maintains counters in memory. Under serverless cold starts across multiple lambda instances, counters reset. This is standard behavior for serverless and does not break application functionality.
