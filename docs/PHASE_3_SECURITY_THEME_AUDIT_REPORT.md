# Phase 3E — Admin Panel Screen Audit

## Scope and evidence

The inventory below is based on the route tree in `frontend/src/App.tsx`, the admin page components, `frontend/src/services/api.ts`, and the corresponding backend auth/admin routes. There are 17 admin route declarations: the login route, the protected workspace index, 14 workspace screens, and the protected wildcard screen. Account security is a tab of Site Settings, not a separate route.

Frontend production build and TypeScript check passed. The updated integration script passed all 46 checks, including Phase 3E regressions. Oxlint exits successfully with non-blocking warnings across multiple screens and layout components (state-in-effect, fast-refresh, and render-purity rules). Browser rendering was inspected at desktop and narrow/mobile viewport sizes for the login screen, including label association and page-width overflow. A direct unauthenticated navigation to `/admin/users` redirected to `/admin/login`. No visual verification is claimed for authenticated screens: the local backend/database was unavailable, so their API-driven pages and dialogs could not be exercised in a browser.

## Cross-cutting findings and changes

- The protected layout redirects unauthenticated sessions to login and preserves the requested path. The `users` screen has a frontend role guard; the backend independently guards user-management APIs with `requireSuperAdmin`. Other authenticated content routes intentionally use the general `requireAuth` policy.
- Added admin-scoped focus-visible styling, long-content wrapping, a breadcrumb, accessible mobile navigation controls, and Escape-to-close behavior. Public-site global styling was not changed.
- Removed misleading local/fixture persistence claims from the settings, sections, and media flows. Media fixture records are no longer presented as server data.
- Passwords/tokens are not added to UI messages. Removed raw login and refresh-request error logging that could include request configuration.
- No database connection, migration, seed, schema change, or TiDB work was performed.

## Verification and limitations

- `npm run build` in `frontend`: passed (TypeScript and Vite production build); Vite reports the existing large JavaScript chunk warning.
- `npm run lint` in `frontend`: passed with non-blocking state-in-effect, fast-refresh, and render-purity warnings in multiple components.
- `node frontend/test-integration.cjs`: passed all 46 checks, including seven Phase 3E regression assertions.
- Browser: login page rendered and was inspected at desktop and narrow/mobile sizes; no horizontal document overflow was observed in the measured viewports. Direct unauthenticated access to `/admin/users` redirected to the login route.
- API/fixture behavior, forms, destructive confirmations, editor/super-admin live permissions, backend error states, tablets, and authenticated screen visuals remain unverified because no usable backend/database session was available. Source inspection is not reported as visual verification.
- The audit is source-complete for the admin route declarations, but some existing CRUD pages still need visible load-error states, consistent field-label associations, and live authenticated responsive/accessibility verification. These are recorded above rather than described as completed.
